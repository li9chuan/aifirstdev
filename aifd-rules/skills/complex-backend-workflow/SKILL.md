# 复杂后端流程

核心原则：先定层，再定义；先冻结上层，再允许下层实现。

## L0-L5 分层

- L0 目标：说明为什么要做，成功后用户或工程获得什么能力。
- L1 术语：冻结名词、边界、参与对象和不变量。
- L2 真相源：明确状态、配置、协议、持久化、生成物各自的拥有方。
- L3 运行模型：说明生命周期、恢复、并发、失败、幂等和版本兼容。
- L4 落地计划：拆成可验证的小批次，每批次有主修改面和验收方式。
- L5 验证：列出单测、示例、兼容性检查、构建和人工验收。

## 工作流

1. 先使用 `architecture-and-surface-routing` 判断主修改面。
2. 冻结 L0-L3，不在术语和真相源未定时写代码。
3. 按 L4 拆成最小可交付批次。
4. 每批次只修改拥有职责的模块，并补齐必要联动。
5. 每批次结束时更新验收结果和未覆盖风险。

## 必须冻结的问题

- 哪个模块拥有状态真相。
- 哪些字段来自配置，哪些字段来自运行态，哪些字段来自协议输入。
- 启动恢复从哪里重建，失败时保留什么。
- 每个阶段的持久 marker 与外部副作用顺序是什么。
- 热更、重启、重复请求和超时如何处理。
- 旧版本业务项目如何升级或继续兼容。

## 外部副作用与状态落盘

- 复杂状态机必须说明每个阶段先写入哪些持久 marker，再执行哪些外部副作用。
- Redis/DB/account 创建、文件写入、队列发布、通知发送等外部副作用不能只靠内存状态承诺。
- 如果副作用必须先于状态落盘，必须设计可重试判断或补偿策略，并说明重复执行是否安全。
- 一次性工具可以降低工程化程度，但计划或审查中仍要明确失败窗口、人工恢复方式和不自动补偿的理由。

## 验收门禁

- 方案必须能说明主修改面、联动面和不修改面。
- 每个批次必须有可运行或可静态验证的验收项。
- 配置、schema、持久化或 runtime 合约变更必须说明兼容策略。
- 无法验证的项必须在交付中明确原因和残余风险。
