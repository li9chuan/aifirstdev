# 提交描述

这个 skill 用于最终交付阶段。只要本轮产生了文件修改，并且需要给用户给出提交描述，就按这里组织“提交描述”。

## 输出位置

- 最终交付中单独给出 `提交描述：`。
- 不代替用户执行提交。
- 如果本轮没有文件修改，不需要给提交描述。

## 标题格式

提交标题首个方括号必须写模块标签：

```text
[aifd-tools] 增加 NSIS makensis 工具支持
```

规则：

- 第一个 `[]` 写主修改模块。
- 模块标签使用稳定项目或业务模块名，例如 `aifd-rpc`、`aifd-proxy`、`aifd-rules`、`minigame`、`desktool`。
- 多模块但必须一起生效时，使用主拥有模块作为标签，正文说明联动模块。
- 多个互不依赖的功能可以给多条提交描述；必须一起生效的改动不要强拆。
- 标题保持一行，使用表达真实行为的具体动词，避免“调整”“优化”这类空泛动词。

## 正文格式

正文使用 1-3 条关键改动，最后一条写验证：

```text
[aifd-rules] 增加提交描述 skill

- 新增提交标题模块标签和正文组织规则
- 更新 skill map 和 agent 入口
- 验证：文档结构检查
```

正文规则：

- 只写对提交者有用的信息，不复述所有文件名。
- 有 proto / cfgtable / 生成物 / C++ / Go service 联动时必须说明。
- 验证写实际运行过的命令或明确未运行原因。
- 文档-only 修改可以写 `验证：文档结构检查` 或具体搜索命令。
- 不要把“项目级经验”混进提交描述；经验沉淀另放最终说明。

## 模块标签选择

优先级：

1. 直接拥有主行为的 aifd 子项目，例如 `aifd-rpc`、`aifd-rdb`、`aifd-tools`。
2. 示例项目，例如 `minigame`、`desktool`。
3. 规则或 skill 修改使用 `aifd-rules`。
4. 业务项目使用业务模块名或 feature 名，例如 `auth`、`guildwar`。

## 拆分建议

- 同一框架能力的代码、测试、README 和 lockfile 属于一条提交。
- 运行时代码与生成物必须一起生效时不要拆开。
- 纯文档经验沉淀可以独立提交。
- 示例项目和框架库如果只是为了演示同一 API 变更，优先合并为同一条提交，并在正文说明示例联动。
